# Hakoni — vision and open questions

**Question this document answers:** what is Hakoni trying to show, where does the idea come from, and what is still open?

Written on 24 November 2026 from the author's notes, before any plan step runs. It records hypotheses and directions, **not decisions**: no architecture, runtime or file name is fixed here. Earlier working names: *Agent X*, then *Seed*.

## 1. Starting point

Agents are becoming useful to people who are not developers, but handing one over is still hard. The starting point is **packaging, securing and distributing agents, with the container as the delivery unit**, and a sandbox runtime (OpenShell is the first candidate, from the author's own experiments) to isolate what the agent can do on a workstation.

## 2. Experiences behind the idea

### An agent onboarded through one Markdown file

A normal human (i.e. non-developer) contributing to a technical project received **a link to an onboarding Markdown file in Git**, not an application to install. Their own coding agent read it. The document explained:

- what the project is, its history and what has been done;
- where and how to work together;
- how to clone the repository, join a branch reserved for the agent and take ownership of its working folder;
- how to prepare the environment: dependencies, build tools;
- where to find the work plan, an evolving plan whose first steps only are defined;
- how to join a chat channel and follow a small communication protocol, through the agent's chat connector.

The agent then had a communication channel, a shared Git space (its branch and folder) and an environment it prepared itself. It worked from its user's business instructions and asked the project owner for technical guidance when needed. Human validations were part of the process.

**Lesson:** the onboarding file already acts as an *agentic bootstrap*. It describes a technical environment, but also a mission, a place in the project's organisation and collaboration conventions.

### The same pattern, between agents

The same mechanism is now routine in [TANSTAAFLLM](https://github.com/mdussere/tanstaafllm), a multi-agent project where several agent sessions work side by side, one per workline. When a new topic opens, an orchestrator agent creates the workline: it prepares a place for the incoming agent (its folder and plan), the environment that agent will need, and an onboarding document. The new agent session starts from that document alone. It works well.

Hakoni's own first coding agent joined the same way, from [its onboarding document](0000_02_onboarding.md).

**Lesson:** an onboarding document is not only for a human's agent joining from outside: it is the ordinary way to bring any new agent into a project, and another agent can write it. The recipe for writing one is not yet captured as a skill.

### A sandbox as a business unit

A specialised sandbox container is used to investigate production alerts. It holds:

- **authorised providers and tools:** read access to observability, data-warehouse, LLM-tracing and ticketing tools, through their CLIs;
- **embedded skills:** investigation methods, what to look at, which sources to check, collection limits, business rules;
- configuration, small shell utilities (access checks), dependencies, and a local folder layout for intermediate artifacts and reports.

Outside the sandbox: the tooling that refreshes connections and single sign-on. No personal secret is baked into the package. The coding agent connects to the sandbox over SSH; **nothing business-specific is installed on the agent's side**.

In a new conversation, a plain request such as *"Was there an alert in the last hour? What happened?"* is enough: the agent discovers the sandbox's context and procedures, queries the authorised sources, investigates and writes its artifacts where expected. The project does not need re-explaining at each conversation.

**Lesson:** the agent client and the business package are separate. Another agent can be reconnected without rebuilding the context by hand. Portability to a second client (Claude Code after Codex, or the reverse) is still to be tested: skill discovery, conventions and runtime may differ. The model does not need to live in the container.

**Not to be confused:** the onboarding experiences above did not use a sandbox. Bringing the two together is precisely the Hakoni idea.

## 3. Hypothesis: small agentic environments as a successor to spreadsheet tooling

A large share of everyday business computing runs on spreadsheets and hand-made assemblies built by business teams, outside any IT project. How large that share is has not been measured: it is an intuition, not a statistic.

Hakoni explores a possible successor: **small, specialised agentic containers**, autonomous enough to carry a business activity, usable by non-developers on their workstation, and distributable without a dedicated application infrastructure for each use.

The analogy is about **the unit of distribution and ownership**, not about replacing a spreadsheet's deterministic calculations:

- a spreadsheet bundles data, calculation logic, presentation and business practice in one transmissible artifact;
- a Hakoni could bundle instructions, skills, tools, dependencies, conventions, access policies and a workspace in one transmissible artifact;
- an interchangeable agent client lets the user drive it in natural language;
- shared spaces and channels extend individual use to cross-team collaboration.

The aim is to keep the closeness, agility and low friction of informal business computing, while improving control, isolation, reproducibility and collaboration. "No heavy infrastructure" means no new central platform for each small use; it does not mean offline, nor independent of identity services, model providers or data sources.

Provocative title for a possible talk, much later: **"Can we finally kill Excel?"**

## 4. One Git link as the unit of distribution

The decisive test is simplicity: **sending one onboarding link should be enough** for someone whose agent is a general-purpose one.

Envisaged path, to prototype (not validated end to end):

1. The author prepares a Git repository with the onboarding document, the container recipe (for example a Dockerfile and a sandbox policy), the skills, tools and working conventions.
2. They send only the onboarding link; the recipient gives it to Claude Code, Codex or another compatible agent.
3. The agent reads the instructions, detects missing prerequisites (sandbox runtime, container engine), explains them and asks permission before installing. It assumes neither admin rights nor implicit consent.
4. It fetches the recipe, builds and starts the container.
5. It connects to the container (SSH is the first candidate) once authorised, and continues the bootstrap inside the isolated environment.
6. It configures Git access with the recipient's own identity and rights, clones the repository, joins or creates the right branch, installs what the work needs and starts working.
7. It joins the collaboration mechanisms already defined in the repository.

Installation is therefore **a task given to a general-purpose agent**, not a manual for a business user. The initial bootstrap may act outside the sandbox: it is a trust boundary to handle explicitly (repository provenance, recipe review, minimal permissions, no blind execution of remote code).

### Git as the plane for distribution, collaboration and continuity

Git could carry:

- the recipe and the environment's instructions;
- versioned knowledge, skills, conventions and work plans;
- collaboration through branches, contributions and validations;
- an explicit work log: actions, notable events, results, lessons and shareable decisions;
- continuity between sessions: at each restart, a fetch shows what changed while the agent was away, and the agent reviews it before resuming. A fetch does not change the workspace by itself; merging updates and conflicts follows an explicit policy.

The Git log is a versioned working memory, distinct from full execution telemetry. Conversations, secrets, sensitive traces or raw business data are not pushed by default. Package updates, shared knowledge and personal state are kept apart; a sync never overwrites local work. Using Git internally must not force business users to learn Git.

**Structuring hypothesis:** the Git link is the transmissible entry point; the repository is the construction and coordination plan; the container is the work environment; the agent client installs it and then drives it.

### A projected scenario: a sparring partner handed to friends

A projection, not a design: how a finished Hakoni could travel from its author to other people.

Three words to tell its parts apart:

- **The essence**: the original Git repository, the starting guide and the structure of this agent, as its author prepared it.
- **An instance**: an OpenShell container created from the essence on someone's computer. One person can run several instances.
- **The persistence**: that person's own copy of the original repository. It holds their logs and their changes, and whatever they build together with the agent. When they are happy with a change, they propose it back to the essence, for example with a pull request.

**The essence.** We have built a personal work companion, not a colleague's tool but a sparring partner: we discuss and exchange ideas with it, and it keeps things for us. We have standardised it into a Hakoni: a Git repository holding the ideal companion, a set of tools that go with it (it knows how to do things, it can produce reports), the dependencies we like for those tools. Everything is prepared. The onboarding document is the guide written by the person who prepared this companion. This repository is the essence.

**Handing it over.** We talk friends into using it too. Each friend:

1. Makes their own copy of our repository, to grow their own companion, and keeps that copy private: their persistence.
2. Gives their coding agent (say Claude Code, in a first session on the host) the link to the onboarding file of their copy.

**Planting, from the host session.** The agent reads the onboarding file, then, asking before each sensitive action:

3. installs the missing dependencies;
4. sets up the providers, so that the sandbox gets the authorisations it needs;
5. creates the OpenShell container: an instance;
6. prepares the SSH connection, tests it, and creates the agent client's own remote connection to the sandbox;
7. through that connection, runs a remote command that clones the friend's copy of the repository inside the sandbox;
8. tells its user to switch to the new session, the one that runs inside the sandbox.

**Growing, inside the box.** In the new session, the agent finds itself in the clone, at the start of the story: it prepares its environment, reviews the plan and starts working. With VS Code, the editor connects over SSH to the same sandbox, so that development happens directly in the Git clone inside it.

**Points to check** (assumptions, not facts):

- Checked in GitHub's documentation (2026-11-24): a fork of a public repository is public, and its visibility cannot be changed on its own ([forks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/about-permissions-and-visibility-of-forks)). A private persistence is therefore a separate repository: a duplicate (`git clone --bare`, then `git push --mirror` to a new private repository, [duplicating](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository)) or a repository created from a template, which starts from a single commit ([templates](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template)). Neither keeps a documented pull-request link to the essence: the only documented pull-request route is a public fork. Contributing back from a private persistence needs another path (for example a public fork used only for contributions, or patches); to design.
- Whether and how each agent client opens a session on a remote machine over SSH (Claude Code, Codex, VS Code Remote-SSH): Step 2 of the plan.
- The host session does the planting, the sandbox session does the work: two trust zones, and a hand-over between them that the user performs.

## 5. Hakoni builds Hakoni

The first Hakoni project is Hakoni itself (dogfooding). Instead of building the demonstrator in a classic setup and presenting it afterwards, use the distribution, onboarding and collaboration mechanism from the start.

- Entry point: a single link to an onboarding Markdown file, *the seed*.
- Give exactly the same link to Codex and to Claude Code, with no client-specific preparation.
- The agent handles, with the needed permissions: prerequisites, building and starting the container, connecting to it, the Git bootstrap, preparing the workspace and resuming the plan.
- Contributors join with the same seed, get their own workspaces, share progress and pick up changes.
- Improvements to the onboarding and packaging are versioned, then tried by new installs and sessions. Keep a reference version and a way back; an update of the bootstrap never authorises changing the sandbox or permissions without control.

Every difficulty met while developing Hakoni with Hakoni reveals a real product friction: the reflexive setup is also an evaluation tool.

Vocabulary, not fixed: **seed** (the onboarding artifact or its link), **plant** (installing and initialising the environment), **grow** (developing, collaborating, enriching it).

## 6. Sandboxing as the foundation of the package

The central metaphor is a small, functional, autonomous entity, not distributed intelligence as such. The environment has its tools, knowledge, rules and working memory; it can collaborate and exchange with the outside within its permissions. Autonomous does not mean offline, nor independent of a remote model.

### What a Hakoni is made of

A Hakoni, the box, is a sandbox, and the sandbox is also a container. Five parts can be told apart. The terms below take OpenShell as the reference runtime; Step 2 of the plan checks them.

1. **The container.** The image and the dependencies installed on it: system packages, languages, CLIs, tools. As with any container image, what is installed on it decides what it can do.
2. **The knowledge.** What the box knows: instructions, skills, business rules, procedures, reference data. It is the content of the box, versioned separately from the image.
3. **The interface with the outside.** The sandbox configuration and policies, and the *providers* through which the box reaches external services, including the providers of secrets. The box gets access through them; it does not hold credentials of its own.
4. **The outside tooling.** Tools that run on the host, outside the sandbox, to prepare the providers: generate them, grant them rights, and create and renew their credentials while the sandbox is running. This is a key point: a box that works for one day is easy; keeping its access alive is the real work.
5. **The memory.** Communication plus persistence: what the box remembers between sessions and shares with others (work log, shared knowledge, exchanges). Work started on shared memory in [TANSTAAFLLM](https://github.com/mdussere/tanstaafllm) may feed this part; it is not detailed here yet.

### Principles

- The container is the delivery unit and the perimeter of the mission, **not a security guarantee on its own**.
- Separate the host bootstrap (prerequisites, build, start) from the business work inside the sandbox. Host permissions are not inherited implicitly; sensitive actions need explicit authorisation.
- Version in Git the build recipes, dependencies, security rules, business instructions, tools and validation checks. Review sensitive changes before activating them; check the provenance of recipes and images.
- Least privilege: explicit file access and mounts, allowed outbound network and services, the user's own identity and secrets, resource limits, no Docker socket or privileged host access by default.
- Keep the agent interchangeable: connect through a controlled interface (SSH as a first candidate), without assuming that Codex and Claude Code offer the same guarantees. Inference may stay remote; state which data leaves the perimeter.
- Separate durable state, shared knowledge and the rebuildable environment. Log useful events without publishing secrets or raw business data; plan for stop, revocation, rebuild and rollback.
- Onboarding documents and fetched content stay **untrusted input** until their provenance and permissions are validated. An instruction in a repository cannot, on its own, authorise leaving the trust perimeter.

Sandboxing is not only protection: it delimits, and makes transmissible, the small business world that a Hakoni is, provided the controls are effective.

## 7. Success criteria for a first demonstrator

From the same onboarding link, on two separate installs, two different agent clients should:

- reach an equivalent, working environment without client-specific manual steps (apart from legitimate authorisations and authentications);
- do an authorised task;
- produce a Git contribution;
- resume a session and catch up on what changed.

Security checks to pass:

- an out-of-policy file access, network call or command is effectively refused;
- no secret leaks into the repository, the logs or the image;
- business instructions cannot raise permissions.

Document the differences between clients, the initial approvals and the real limits of the runtime. **None of these tests has been run yet.**

## 8. Open questions

- What exactly is the transmissible artifact: image, manifest, build recipe, policies, skills, tools, templates, initial data?
- What goes where: versioned image, organisation configuration, user identity and secrets, persistent workspace, shared knowledge?
- What should be fixed in the package, and what should the agent discover, configure or negotiate when it arrives?
- How to keep the ease of sending a spreadsheet while controlling provenance, updates, rights, costs, logging and life cycle?
- How to make the package independent of the agent client when clients do not discover the same skills natively?
- How to keep deterministic calculations and validations where business reliability needs them?
- Which everyday uses make good first candidates: investigation, reporting, specialised analysis, collaboration and validation?
- Does communication go directly between agents, or through shared artifacts and spaces?

## 9. Name and look

**Hakoni**: an invented contraction of *hakoniwa* (箱庭), a miniature garden in a box. The name has not been checked legally. The visual identity explored so far is sober and calm: a small living garden in a container, with a limited natural palette. On 2026-11-24 Michaël chose the closable-box logo in a contemporary Japan palette (indigo, vermilion, off-white); it is in `site/assets/hakoni-logo.svg`. The photo that inspired it is not attributed yet.
